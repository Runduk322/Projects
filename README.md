# ofd-analytics — аналитика чековых данных ОФД

![CI](https://github.com/Runduk322/Projects/actions/workflows/ci.yml/badge.svg)

Пакет для анализа чеков из выгрузки ОФД: приводит «файл, который дали» к
рабочей таблице и считает метрики, которые в ритейле реально принимают решения —
RFM-сегменты покупателей, ABC/XYZ ассортимента, связки товаров в корзине,
когортное удержание и динамику продаж.

Сделан как мост из BI в Data Science: задачи здесь знакомые аналитику
(группировки, доли, накопленные суммы), но инструмент — pandas, а не SQL, и
каждый расчёт закрыт тестами.

## Быстрый старт

```bash
git clone https://github.com/Runduk322/Projects.git
cd Projects
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -e ".[dev]"

ofd demo --outdir build/demo
```

`ofd demo` прогоняет весь пайплайн на **синтетических** данных: генерирует
выгрузку в формате ОФД (с типичным мусором), чистит её и собирает отчёт.
В `build/demo` появятся `report.md`, `cleaning_report.md` и 13 CSV-таблиц.

## Как подставить свои данные ОФД

Синтетика нужна только чтобы проект был запускаемым и тестируемым без приватных
данных. На своей выгрузке пайплайн работает так же:

```bash
ofd clean   --input выгрузка_ОФД.csv --output data/clean.csv \
            --period 2025-01-01 2025-12-31 --report reports/cleaning.md
ofd analyze --input data/clean.csv   --outdir reports/
```

Или из Python:

```python
from ofd_analytics import read_receipts, clean_receipts, analyze

raw = read_receipts("выгрузка_ОФД.csv")  # cp1251 и «;» определяются сами
clean, cleaning = clean_receipts(raw, period=("2025-01-01", "2025-12-31"))
print(cleaning.to_markdown())  # что именно изменилось в данных

result = analyze(clean)
result.save("reports/")
print(result.kpi["avg_ticket"], result.kpi["revenue"])
```

Заголовки колонок распознаются автоматически: «Номер ФД», «Дата и время»,
«Наименование товара», «Кол-во», «Сумма, руб.», «Признак расчёта» и ещё десятки
вариантов из разных ОФД. Если вашего варианта нет — добавьте строку в
`COLUMN_ALIASES` в [`src/ofd_analytics/schema.py`](src/ofd_analytics/schema.py),
это единственное место, где описано соответствие.

Чего не хватает — видно сразу: `clean_receipts` падает с понятным сообщением,
если нет обязательной колонки, а RFM и когорты пропускаются с пометкой в отчёте,
если в выгрузке нет `customer_id` (в чеках ОФД покупатель известен только там,
где привязан телефон, e-mail или карта лояльности).

### Приватность

Каталоги `data/` и `reports/` в `.gitignore`: чековые данные содержат телефоны и
e-mail покупателей, их нельзя коммитить в репозиторий. Пакет ничего не отправляет
по сети — все расчёты локальные.

## Каноническая схема

Одна строка таблицы — одна позиция в чеке.

| колонка | обязательна | смысл |
| --- | --- | --- |
| `receipt_id` | да | номер фискального документа, ключ чека |
| `receipt_dt` | да | дата и время чека |
| `item_name` | да | наименование позиции |
| `qty` | да | количество |
| `price` | да | цена за единицу |
| `line_sum` | нет | сумма позиции; у возвратов отрицательная |
| `store_id` | нет | торговая точка или ККТ |
| `customer_id` | нет | покупатель: телефон, e-mail, карта лояльности |
| `category` | нет | товарная группа |
| `vat_rate` | нет | ставка НДС |
| `payment_type` | нет | `cash`, `card`, `prepaid` |
| `operation` | нет | `sale` или `return` |

Два решения в схеме, о которых стоит знать:

* **возвраты уходят в минус.** В выгрузке ОФД возврат помечен признаком расчёта,
  а суммы положительные. После очистки `qty` и `line_sum` у возвратов
  отрицательные, поэтому суммы складываются напрямую и `revenue` — это сразу
  чистая выручка.
* **сумма позиции главнее цены.** При расхождении `line_sum` и `qty × price`
  по умолчанию пересчитывается цена: в фискальном документе сумма — это реально
  оплаченные деньги, включая скидку. Обратное поведение — `sum_strategy="price"`.

## Что считает пакет

| модуль | вопрос | ключевые функции |
| --- | --- | --- |
| `clean` | можно ли доверять данным | `clean_receipts`, `CleaningReport` |
| `features` | сколько чеков и какой средний чек | `receipt_totals`, `kpi_summary` |
| `analytics.rfm` | кто наши покупатели и кого мы теряем | `rfm`, `segment_summary` |
| `analytics.abc` | что приносит деньги и что стабильно | `abc_analysis`, `xyz_analysis`, `abc_xyz` |
| `analytics.basket` | что покупают вместе | `pair_rules`, `item_support` |
| `analytics.timeseries` | как продажи меняются во времени | `revenue_by`, `weekday_profile`, `hour_profile` |
| `analytics.cohorts` | возвращаются ли покупатели | `cohort_matrix`, `retention_rates` |
| `report` | собрать всё в один документ | `analyze`, `AnalysisResult.save` |

Как читать каждую метрику и где на ней легко ошибиться —
в [`docs/methodology.md`](docs/methodology.md).

## Отчёт об очистке

Очистка никогда не молчит: каждый шаг считает затронутые строки. Так видно,
что «выручка упала» — это не потеря данных, а удалённые дубли.

```
### Очистка данных

- строк на входе: **4 030**
- строк на выходе: **3 877**
- удалено: **153** (3.80%)

| шаг | строк | комментарий |
| --- | ---: | --- |
| унифицированы наименования | 336 | регистр и пробелы |
| удалены полные дубли строк | 80 |  |
| восстановлена сумма позиции | 161 | price × qty |
| восстановлена цена | 161 | line_sum / qty |
| устранено расхождение суммы | 190 | сумма главная, пересчитана цена |
| удалены строки с непозитивным количеством | 66 |  |
| удалены невозможные даты | 7 | вне [2016-01-01, 2026-01-01] |
| возвраты переведены в минус | 131 | qty и line_sum |
```

## Команды CLI

```bash
ofd generate --output data/raw.csv --receipts 5000 --messy --ofd-style
ofd clean    --input data/raw.csv --output data/clean.csv --period 2025-01-01 2025-12-31
ofd analyze  --input data/clean.csv --outdir reports/ --top 15
ofd demo     --outdir build/demo
```

`ofd <команда> --help` покажет все параметры.

## Структура проекта

```
src/ofd_analytics/
├── schema.py          каноническая схема и синонимы заголовков выгрузок
├── io.py              чтение CSV (cp1251, «;») и Parquet
├── clean.py           нормализация, очистка, отчёт об изменениях
├── generate.py        генератор синтетических чеков с сезонностью и связками
├── features.py        переход позиция → чек, сводные показатели
├── report.py          сборка Markdown-отчёта и CSV-таблиц
├── cli.py             команды generate / clean / analyze / demo
└── analytics/         rfm · abc · basket · timeseries · cohorts
tests/                 173 теста, покрытие 98%
examples/walkthrough.py   тот же пайплайн кодом, шаг за шагом
docs/methodology.md    как читать метрики
```
